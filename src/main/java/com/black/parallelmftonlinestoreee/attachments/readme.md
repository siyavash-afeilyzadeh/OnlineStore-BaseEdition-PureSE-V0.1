# Attachments module — the template for every module

An **attachment** is a file that belongs to something else: a product photo, a user document, an organization contract...
The module keeps the file on **disk** and its details in the **database**: owner, title, description, keywords,
file name, file type and file size.

It is deliberately simple and complete: it uses every layer of the architecture exactly once,
so **every other module should be written by copying it** and renaming. The file part (section 5) is extra:
a normal module does not need it.

## 1. Package layout

```
attachments/
├── entity/        Attachment                  the table (JPA entity)
│   └── enums/     AttachmentOwnerType         what an attachment can belong to (PRODUCT, USER, ...)
├── dto/           AttachmentRequest           what the client sends (create and update)
│                  AttachmentDto               what the client receives
│                  AttachmentContent           a file ready to be downloaded (service -> API)
├── mapper/        AttachmentMapper            entity <-> dto, the code is generated by MapStruct
├── repository/    AttachmentRepository        database access
├── storage/       FileStorage                 disk access: save and open files
├── exception/     DuplicateFileNameException  a business rule was broken
├── service/       AttachmentService           WHAT the module can do (interface)
│   └── impl/      AttachmentServiceImpl       HOW: business rules + transactions
└── rest/          AttachmentApi               HTTP endpoints under /api/v1/attachments
```

Every layer only talks to the layer below it:
`rest -> service -> repository -> database` (and `service -> storage -> disk` for the file).
The mapper and the DTOs are used by the service.

## 2. How a request flows

Creating an attachment takes **two requests**: first its details as JSON, then the file itself.

```
 client
   |  POST /api/v1/attachments   {"ownerType":"PRODUCT","ownerId":5,"title":"Invoice","fileName":"a.pdf"}
   v
 AttachmentApi            1. JSON -> AttachmentRequest (JSON-B)
   |                      2. @Valid checks the request     -> 400 if invalid
   v
 AttachmentServiceImpl    3. transaction starts (@Transactional)
   |                      4. business rule: file name free for this owner? -> 409 if not
   |                      5. mapper: AttachmentRequest -> Attachment
   v
 AttachmentRepository     6. entityManager.persist(...)  -> INSERT
   |
   v
 AttachmentServiceImpl    7. mapper: Attachment -> AttachmentDto
   |                      8. transaction commits
   v
 AttachmentApi            9. 201 Created + AttachmentDto (id = 1, no file yet)
   |
   v
 ApiResponseFilter        10. core wraps the dto: {"data": {...}, "status": 201, "success": true, ...}

 client
   |  PUT /api/v1/attachments/1/content      body = the file bytes, Content-Type: application/pdf
   v
 AttachmentApi            the body arrives as an InputStream
   v
 AttachmentServiceImpl    FileStorage writes it to disk under a new name,
                          the attachment gets contentType, fileSize, storedName -> 200 + AttachmentDto
```

When something goes wrong nobody writes `try/catch`: the exception travels up and a mapper in
`core/rest/exception` turns it into the same JSON shape for every module (see [7.3](#73-error-responses)).

## 3. Implementation order, step by step

Each step only needs the previous ones, so the project compiles after every step.

### Step 1 — Entity  (`entity/Attachment.java`, `entity/enums/AttachmentOwnerType.java`)

```java
@Entity
@Table(name = "attachments", indexes = @Index(columnList = "ownerType, ownerId"))
@SQLDelete(sql = "update attachments set deleted=true, deleted_at=current_timestamp where id=? and version=?")
@SQLRestriction("deleted = false")

@NoArgsConstructor
@Getter
@Setter
@SuperBuilder

public class Attachment extends BaseEntity {

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 30)
    private AttachmentOwnerType ownerType;

    @Column(nullable = false)
    private Long ownerId;

    @Column(nullable = false, length = 100)
    private String title;

    @Column(nullable = false)
    private String fileName;

    @Column(length = 500)
    private String description;

    @Column(length = 500)
    private String keywords;

    // filled when the file itself is uploaded (section 5)
    @Column(length = 100)
    private String contentType;

    private Long fileSize;

    @Column(length = 100)
    private String storedName;
}
```

| Part | Why |
|---|---|
| `extends BaseEntity` | `id`, `version`, `deleted`, `createdAt`, `updatedAt`, `deletedAt` come for free |
| `@Table(name = "attachments")` | the table name; `BaseRepository.restore()` also needs it |
| `indexes = @Index(...)` | the most common search is "attachments of one owner", the index makes it fast |
| `@SQLDelete(...)` | `remove()` does **not** delete the row, it runs this UPDATE (soft delete) |
| `@SQLRestriction("deleted = false")` | every query automatically skips soft-deleted rows |
| `@Enumerated(EnumType.STRING)` | stores `PRODUCT`, not a number (section 4) |
| `@Column(nullable = false, length = ...)` | the database columns match the validation of the request |
| `@NoArgsConstructor` | JPA needs a no-arg constructor |
| `@SuperBuilder` | a builder that also knows the `BaseEntity` fields (used by MapStruct and by the tests) |

| Field | Filled by |
|---|---|
| `ownerType`, `ownerId`, `title`, `fileName`, `description`, `keywords` | the client (the request) |
| `contentType`, `fileSize`, `storedName` | the server, when the file is uploaded; empty until then |

- `keywords` is one text column, for example `"invoice, 2026"`. Simple; a search uses `like`.
- There is no unique constraint on `fileName`: a soft-deleted row keeps its file name,
  so the rule "unique per owner" is checked in the service among the rows that are not deleted.

Rules:
- The table name must be **the same** in `@Table` and `@SQLDelete`.
- Never redeclare `id`, `version`, `createdAt`, ... — they are in `BaseEntity`.
- No `@ToString` / `@Data` on entities: with relations they load lazy data or loop forever.
- Relations (`@ManyToOne`, ...) go here; the DTOs only carry the id of the related entity.

### Step 2 — Repository  (`repository/AttachmentRepository.java`)

```java
@ApplicationScoped
public class AttachmentRepository extends BaseRepository<Attachment> {

    public AttachmentRepository() {
    }

    public AttachmentRepository(EntityManager entityManager) {
        super(entityManager);
    }

    @Override
    protected Class<Attachment> entityType() {
        return Attachment.class;
    }

    public List<Attachment> findByOwner(AttachmentOwnerType ownerType, Long ownerId) {
        return entityManager
                .createQuery("select a from Attachment a"
                        + " where a.ownerType = :ownerType and a.ownerId = :ownerId"
                        + " order by a.id", Attachment.class)
                .setParameter("ownerType", ownerType)
                .setParameter("ownerId", ownerId)
                .getResultList();
    }

    public Optional<Attachment> findByOwnerAndFileName(AttachmentOwnerType ownerType, Long ownerId, String fileName) {
        // same idea, one more condition; getResultStream().findFirst() gives an Optional
    }
}
```

- `@ApplicationScoped` makes it a CDI bean (with `bean-discovery-mode="annotated"` a class without it is invisible to `@Inject`).
- The no-arg constructor is for CDI; the one with `EntityManager` is for the tests (no CDI there).
- `entityType()` is the only thing `BaseRepository` needs to know.
- The finders use **JPQL** with the inherited `entityManager`: entity and field names (`Attachment`, `a.ownerType`),
  never table or column names. Parameters (`:ownerId`) are always bound with `setParameter`, never glued into the text.
- A finder on **one** field can use the inherited helper instead: `findOneBy("fileName", fileName)`.

What `BaseRepository` already gives you:

| Method | Does |
|---|---|
| `save(entity)` | `persist` (INSERT) |
| `update(entity)` | `merge` a detached entity |
| `findById(id)` | `Optional` of the entity |
| `findAll()` / `findAll(page, size)` | all rows / one page, ordered by id |
| `findPage(page, size)` | a `PageResult` with the rows and the totals |
| `count()` | number of rows (not deleted) |
| `delete(entity)` / `delete(id)` | soft delete through `@SQLDelete` |
| `restore(id)` | undo a soft delete |
| `findOneBy("field", value)` | first row whose **entity field** (not column) equals the value |

### Step 3 — DTOs  (`dto/AttachmentRequest.java`, `dto/AttachmentDto.java`)

```java
// Used for both create and update; the id of an update comes from the URL.
public record AttachmentRequest(
        @NotNull AttachmentOwnerType ownerType,
        @NotNull @Positive Long ownerId,
        @NotBlank @Size(max = 100) String title,
        @NotBlank @Size(max = 255) String fileName,
        @Size(max = 500) String description,
        @Size(max = 500) String keywords) {
}

public record AttachmentDto(
        Long id,
        AttachmentOwnerType ownerType,
        Long ownerId,
        String title,
        String fileName,
        String description,
        String keywords,
        String contentType,
        Long fileSize) {
}
```

- **Two records per entity**: a request (in) and a dto (out). Records are immutable and need no Lombok.
- The request has **no id**: the id is in the URL (`PUT /attachments/5`), so a client can never change it.
- The request has no `contentType` / `fileSize` either: the server decides them from the real file.
- The dto has no `storedName`: where the file lies on disk is an internal detail.
- The request carries the validation. Use the right annotation for the type:
  `@NotBlank` only on `String`; `@NotNull`, `@Positive`, `@Size`, `@Email`, ... for the rest (here the enum and the `Long`).
- **Never put an entity in a DTO.** For a relation send its id (`Long categoryId`). An enum is fine.
- The same request is used for create and update: `BaseService<Request, Dto>` has one request type.

`dto/AttachmentContent` (file name, type, size, `InputStream`) is not JSON: the service hands it to the API for a download.

### Step 4 — Mapper  (`mapper/AttachmentMapper.java`)

```java
@Mapper(config = MapStructConfig.class)
public interface AttachmentMapper extends BaseMapper<Attachment, AttachmentDto, AttachmentRequest> {
}
```

One line. `BaseMapper<Entity, Dto, Request>` declares the four conversions and MapStruct writes the code at compile time:

| Method | Used for |
|---|---|
| `toDto(entity)` | every answer |
| `toDtoList(entities)` | lists |
| `toEntity(request)` | create (ignores `id` and `version`) |
| `updateEntity(request, entity)` | update: copies the request into the existing entity (keeps `id` and `version`) |

- `MapStructConfig` makes the mapper a CDI bean (`@Inject` works) and ignores target fields the source does not have.
  That is why `toEntity` and `updateEntity` never touch `contentType`, `fileSize`, `storedName`: the request has no such fields,
  so editing the title of an attachment keeps its file.
- The generated class is `target/generated-sources/annotations/.../AttachmentMapperImpl.java`: open it once, it is plain Java.
  After changing a DTO or the entity, rebuild the project so it is regenerated.
- Fields are matched **by name**. For a relation add one line, for example in a product module:
  `@Mapping(target = "categoryId", source = "category.id")` on an overridden `toDto`.
  Loading the related entity from its id is done in the service, not in the mapper.

### Step 5 — Exception  (`exception/DuplicateFileNameException.java`)

```java
public class DuplicateFileNameException extends BusinessException {

    public DuplicateFileNameException(String fileName) {
        super("This owner already has an attachment with file name '" + fileName + "'");
    }
}
```

- One class per business rule, in the module's `exception` package, extending `core.exception.BusinessException`.
- That is all: `core.rest.exception.GlobalExceptionMapper` already answers every `BusinessException` with **409 Conflict**
  and the message as JSON. No mapper per module, no `try/catch` in the API.
- "Not found" is not a business exception: the service returns an empty `Optional` and the API throws
  `jakarta.ws.rs.NotFoundException` (404).

### Step 6 — Service  (`service/AttachmentService.java`, `service/impl/AttachmentServiceImpl.java`)

```java
public interface AttachmentService extends BaseService<AttachmentRequest, AttachmentDto> {

    List<AttachmentDto> findByOwner(AttachmentOwnerType ownerType, Long ownerId);

    Optional<AttachmentDto> uploadContent(Long id, InputStream content, String contentType);

    Optional<AttachmentContent> findContent(Long id);
}
```

`BaseService` gives `create`, `findById`, `findAll`, `findAll(page, size)`, `update`, `deleteById`;
the module only adds what is special to it: the owner search and the two file methods (section 5).

```java
@ApplicationScoped
@Loggable
public class AttachmentServiceImpl implements AttachmentService {
    @Inject
    private AttachmentRepository repository;
    @Inject
    private AttachmentMapper mapper;
    @Inject
    private FileStorage fileStorage;

    @Transactional
    @Override
    public AttachmentDto create(AttachmentRequest request) {
        checkFileNameIsFree(request, null);
        Attachment attachment = mapper.toEntity(request);
        return mapper.toDto(repository.save(attachment));
    }

    @Transactional
    @Override
    public Optional<AttachmentDto> update(Long id, AttachmentRequest request) {
        return repository.findById(id)
                .map(attachment -> {
                    checkFileNameIsFree(request, id);
                    mapper.updateEntity(request, attachment);
                    return mapper.toDto(attachment);
                });
    }

    @Override
    public PageResult<AttachmentDto> findAll(int page, int size) {
        return repository.findPage(page, size).map(mapper::toDto);
    }

    // ... findById, findAll, findByOwner, deleteById, uploadContent, findContent

    // Business rule: file names are unique per owner. currentId is the attachment being updated (null on create).
    private void checkFileNameIsFree(AttachmentRequest request, Long currentId) {
        repository.findByOwnerAndFileName(request.ownerType(), request.ownerId(), request.fileName())
                .filter(existing -> !existing.getId().equals(currentId))
                .ifPresent(existing -> {
                    throw new DuplicateFileNameException(request.fileName());
                });
    }
}
```

- `@ApplicationScoped` + `@Inject` of the repository, the mapper and the file storage.
- `@Loggable` (from core): every call to the service is logged with its duration, failures as `WARN`.
- **`@Transactional` on every method that writes** (create, update, delete, upload). Without it a write may not be saved
  and lazy relations cannot be loaded. Reads need no transaction.
- `update` does not call `repository.update(...)`: the entity came from `findById` inside the transaction,
  so it is *managed*; changing it is enough, JPA writes the UPDATE at commit (dirty checking).
- `deleteById` calls `repository.delete(...)`; thanks to `@SQLDelete` it is a soft delete.
- Paging: the service's `findAll(page, size)` returns a `PageResult`, so it calls the repository's **`findPage`**
  (the repository's own `findAll(page, size)` returns only a `List`).
- The service works with the **entity** inside and returns **DTOs** outside. It never returns an entity.
- No validation here: it is done in the API (see step 7). `core/readme.md` section 8 explains why.

### Step 7 — REST API  (`rest/AttachmentApi.java`)

```java
@Path("/attachments")
@Produces(MediaType.APPLICATION_JSON)
@Consumes(MediaType.APPLICATION_JSON)
@RequestScoped
@RolesAllowed("admin")
public class AttachmentApi {
    @Inject
    private AttachmentService attachmentService;

    @GET
    @Path("/{id}")
    @PermitAll
    public AttachmentDto getAttachment(@PathParam("id") Long id) {
        return attachmentService.findById(id).orElseThrow(() -> notFound(id));
    }

    @POST
    public Response createAttachment(@NotNull @Valid AttachmentRequest request) {
        return Response
                .status(Response.Status.CREATED)
                .entity(attachmentService.create(request))
                .build();
    }

    // ... getAttachments, getAttachmentsPage, updateAttachment, deleteAttachment,
    //     uploadContent, downloadContent (section 5)

    private NotFoundException notFound(Long id) {
        return new NotFoundException("Attachment " + id + " not found");
    }
}
```

- `@Path("/attachments")` only: `core.rest.RestApplication` already adds `/api/v1`. **Do not repeat `/api/v1` here.**
- `@RequestScoped` makes the class a CDI bean. It is required: without it `@Valid` is ignored
  and a missing bean shows up as a `NullPointerException` at runtime instead of an error at deploy time.
- Inject the **interface** (`AttachmentService`), never the `Impl`.
- `@NotNull @Valid` on the body: `@Valid` checks the fields of the request, `@NotNull` rejects an empty body.
- The API only translates: `Optional` empty -> `NotFoundException` (404), created -> 201, deleted -> 204.
- Return the dto itself, **never** `ApiResponse`: core wraps every JSON answer.
  No business logic and no `try/catch`.
- Security (the pilot for every module): `@RolesAllowed("admin")` on the class makes every method admin only;
  `@PermitAll` opens the reads to everyone, `@RolesAllowed("attachment:file")` lets every user whose roles have
  that permission (in the test data: `admin` and `user`) upload and download the file. A method annotation wins over the class annotation.
  Only on REST classes: on a service these annotations do nothing (see `core/security/readme.md`).
- `getAttachments` takes two optional query parameters: with `?ownerType=PRODUCT&ownerId=5` it returns the attachments
  of that owner, without them all attachments. JAX-RS converts the text `PRODUCT` to the enum by itself.

## 4. Owner: one attachment table for everything

A product, a user and an organization can all have attachments. Instead of one table per owner,
every attachment row says **whose** it is with two columns:

| ownerType | ownerId | title |
|---|---|---|
| `PRODUCT` | 5 | Photo |
| `PRODUCT` | 5 | Manual |
| `USER` | 12 | ID card |

- `AttachmentOwnerType` lists what an attachment can belong to. A new owner = one new enum value.
- **`@Enumerated(EnumType.STRING)` is required.** Without it JPA stores the position (0, 1, 2 ...);
  adding a value in the middle of the enum would then silently move old rows to another owner.
  With `STRING` the column holds the name, so the order does not matter — but **renaming** a value breaks the old rows.
- Enum values are written in capitals (`PRODUCT`, `TICKET_MESSAGE`): they are constants, and the same text is sent in JSON.
- There is no foreign key to the owner, so the database does not check that product 5 exists.
  That is the price of one table for everything; it keeps the attachments module independent of every other module.
- Dependencies go one way: a product module may use `AttachmentService.findByOwner(PRODUCT, id)`;
  the attachments module never imports anything from products, users, ...

## 5. Working with the file

### 5.1 Where the file is

The **file is on disk, its details are in the database**. A database full of files becomes slow to back up and to query,
and loading a file row would pull the whole file into memory.

`storage/FileStorage` is the only class that touches the disk:

```java
@ApplicationScoped
public class FileStorage {

    public StoredFile save(InputStream content) {
        String name = UUID.randomUUID().toString();
        // Files.createDirectories(directory); long size = Files.copy(content, directory.resolve(name));
        return new StoredFile(name, size);
    }

    public InputStream open(String name) { ... }

    public record StoredFile(String name, long size) {
    }
}
```

Four rules, all visible in this class:
1. **The name on disk is a new UUID**, never the name the user sent. Two files called `photo.jpg` do not collide,
   and a name like `../../web.xml` cannot write outside the folder. The original name is kept in the `fileName` column.
2. **The folder is outside the application**: by default `<home>/mft-store/uploads`, or the `STORE_UPLOAD_DIR`
   system property / environment variable (like the `STORE_DB_...` settings). Never inside TomEE's `webapps`:
   a redeploy deletes it.
3. **Streams, not byte arrays**: `Files.copy(InputStream, Path)` copies piece by piece, so a big file never sits in memory.
   It also returns the number of bytes — that is `fileSize`, counted by the server, not trusted from the client.
4. **An `IOException` becomes an `UncheckedIOException`**: the service stays clean, and `GlobalExceptionMapper` answers 500.

Like the repository, `FileStorage` has a second constructor that takes the folder, so the tests use a temporary one.

### 5.2 Upload

```
PUT /api/v1/attachments/1/content
Content-Type: application/pdf
<the file bytes>
```

```java
@PUT
@Path("/{id}/content")
@Consumes(MediaType.WILDCARD)
public AttachmentDto uploadContent(@PathParam("id") Long id,
                                   @HeaderParam(HttpHeaders.CONTENT_TYPE) String contentType,
                                   InputStream content) {
    String type = contentType == null ? MediaType.APPLICATION_OCTET_STREAM : contentType;
    return attachmentService.uploadContent(id, content, type).orElseThrow(() -> notFound(id));
}
```

- The body is the raw file (no JSON, no multipart). `@Consumes(MediaType.WILDCARD)` accepts any type,
  and an `InputStream` parameter receives the body as a stream.
- The file type comes from the `Content-Type` header; without one it is `application/octet-stream` ("some bytes").
- The service saves the file first, then fills `storedName`, `fileSize`, `contentType` in the same transaction.
  If saving the file fails, the attachment is not changed.
- Uploading again replaces the file of the attachment (the old one stays on disk).

### 5.3 Download

```java
@GET
@Path("/{id}/content")
@Produces(MediaType.WILDCARD)
public Response downloadContent(@PathParam("id") Long id) {
    AttachmentContent content = attachmentService.findContent(id)
            .orElseThrow(() -> new NotFoundException("Attachment " + id + " has no file"));
    String fileName = URLEncoder.encode(content.fileName(), StandardCharsets.UTF_8).replace("+", "%20");
    return Response.ok(content.data(), content.contentType())
            .header(HttpHeaders.CONTENT_LENGTH, content.fileSize())
            .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename*=UTF-8''" + fileName)
            .build();
}
```

- `findContent` is empty for a missing attachment **and** for one whose file was not uploaded yet -> 404.
- The entity of the response is an `InputStream`: JAX-RS copies it to the client and closes it.
- `Content-Type` = the stored type, so the browser knows what it is.
- `Content-Disposition: attachment; filename*=UTF-8''...` makes the browser save the file under its original name.
  The name is URL-encoded, so Persian names arrive correctly (`فاکتور.pdf` -> `%D9%81...`).

### 5.4 Delete

Delete is a soft delete, so **the file stays on disk**: `restore(id)` brings back the attachment with its file.
Removing files of deleted attachments for good would be a later cleanup job.

With `hbm2ddl.auto = create-drop` the database is emptied at every deploy but the files stay in the folder:
during development empty the uploads folder now and then.

### 5.5 Left out on purpose

A real product would add: checking the real file type from its content (not only the header), a size limit,
a checksum, a cleanup job for files without a row, a virus scan, and permissions on download.
They are left out to keep the example small.

## 7. REST API

Base URL: `http://localhost:8080/api/v1/attachments` (the port depends on your TomEE configuration).

### 7.1 Endpoints

| Method | Path | Access | Body | Success | Errors |
|---|---|---|---|---|---|
| GET | `/attachments` | everyone | – | 200 list | – |
| GET | `/attachments?ownerType=PRODUCT&ownerId=5` | everyone | – | 200 list of one owner | 404 unknown owner type |
| GET | `/attachments/page?page=0&size=10` | everyone | – | 200 page | 400 (page < 0, size not in 1..100) |
| GET | `/attachments/{id}` | everyone | – | 200 | 404 |
| POST | `/attachments` | admin | `AttachmentRequest` | 201 | 400 invalid, 409 file name taken for this owner |
| PUT | `/attachments/{id}` | admin | `AttachmentRequest` | 200 | 400, 404, 409 |
| DELETE | `/attachments/{id}` | admin | – | 204 | 404 |
| PUT | `/attachments/{id}/content` | `attachment:file` | the file | 200 | 404 |
| GET | `/attachments/{id}/content` | `attachment:file` | – | 200 the file | 404 (no attachment or no file yet) |

`attachment:file` is a permission; in the test data both roles `admin` and `user` have it.
Without login a protected endpoint answers 401, with a login that lacks the role or permission 403.
Test users (only in development, from `META-INF/sql/security.sql`): `admin` / `admin123` and `user` / `user123`.

```json
{"data":{"fileName":"a.pdf","id":1,"keywords":"invoice, 2026","ownerId":5,"ownerType":"PRODUCT","title":"Invoice"},
 "status":201,"success":true,"timestamp":"..."}
```

```bash
curl -u user:user123 -X PUT http://localhost:8080/api/v1/attachments/1/content \
     -H "Content-Type: application/pdf" --data-binary @a.pdf
```
```json
{"data":{"contentType":"application/pdf","fileName":"a.pdf","fileSize":18342,"id":1,"keywords":"invoice, 2026","ownerId":5,
 "ownerType":"PRODUCT","title":"Invoice"},"status":200,"success":true,"timestamp":"..."}
```

```bash
curl -u user:user123 -O -J http://localhost:8080/api/v1/attachments/1/content      # saves a.pdf
curl "http://localhost:8080/api/v1/attachments?ownerType=PRODUCT&ownerId=5"
```

The REST methods return the plain dto; `core/rest/filter/ApiResponseFilter` wraps it in `data` (see core readme).
The downloaded file is never wrapped, and neither is 204 (no body).
Fields that are `null` are left out of the JSON (JSON-B default), e.g. `fileSize` before the upload.
Note: on Windows, Persian text typed directly in a curl command may arrive as `?`; put the JSON in a UTF-8 file
and send it with `--data-binary @body.json`, or use Postman.

### 8.1 Running them

- IntelliJ: right-click the `attachments` test folder (or one class / one method) -> **Run**.
- Maven: `mvnw test` (all tests) or `mvnw test -Dtest=AttachmentServiceImplTest` (one class).
- `mvnw package` runs the tests too; add `-DskipTests` to skip them.

All 30 tests pass. The whole run takes about 40 seconds, mostly Hibernate starting and
a fresh database per database test (simple and isolated, a little slow — acceptable here).

### 8.2 Three kinds of tests

| Kind | Classes | Idea |
|---|---|---|
| **With a real (in-memory) database** | entity, repository | proves that the mapping and the queries really work |
| **With a real (temporary) folder** | storage | proves that files are really written and read |
| **Unit tests with fakes** | mapper, service, API | proves the logic of one class, fast, no database, no disk, no server |

Every test has the same three parts, separated by an empty line: **prepare** the data, **call** one method, **check** the result.

### 8.3 Entity and repository tests — H2 in memory

```java
@BeforeEach
void setUp() {
    emf = Persistence.createEntityManagerFactory("testPU");
    em = emf.createEntityManager();
    repository = new AttachmentRepository(em);
}

@AfterEach
void tearDown() {
    em.close();
    emf.close();
}
```

- `testPU` is defined in `src/test/resources/META-INF/persistence.xml`: an H2 database in memory,
  `hbm2ddl.auto = create-drop`, so **each test starts with empty tables**.
- Only the listed entities exist there: **add a `<class>` line for your entity** when you write tests,
  and one for **every entity it has a relation to** — otherwise Hibernate does not start and every database test fails.
- Outside the server there is no JTA and no CDI, so the tests open and commit transactions themselves
  (`em.getTransaction().begin()` / `commit()`) and pass the `EntityManager` to the repository constructor.

| Test | Proves |
|---|---|
| `persistFillsIdCreatedAtAndVersion` | `BaseEntity` fills `id`, `createdAt`, `version` |
| `ownerTypeIsStoredAsText` | `EnumType.STRING` stores `PRODUCT`, not a number |
| `removeOnlyMarksTheRowAsDeleted` | `@SQLDelete` keeps the row with `deleted = true`, `@SQLRestriction` hides it |
| `titleIsRequired` | `@Column(nullable = false)` is enforced by the database |
| `saveAndFindById` | basic save / find |
| `findByOwner` | only the attachments of that owner, in id order |
| `findByOwnerAndFileName` | found for the same owner, not for another owner |
| `deletedRowsAreNotFound` | soft-deleted rows disappear from every query and from `count()` |
| `findPage` | paging and the totals of `PageResult` |

```java
private final AttachmentMapper mapper = Mappers.getMapper(AttachmentMapper.class);
```

### 8.6 Service and API tests — Mockito

```java
@Mock
private AttachmentRepository repository;                                      // fake: no database
@Mock
private FileStorage fileStorage;                                              // fake: no disk
@Spy

@InjectMocks
```

- `@Mock` — a fake object; every method returns an empty value until you say otherwise.
- `@Spy` — a real object Mockito can watch.
- `@InjectMocks` — creates the class under test and puts the mocks into its `@Inject` fields.
- `MockitoAnnotations.openMocks(this)` in `@BeforeEach` creates them (closed in `@AfterEach`).
- `when(fileStorage.save(content)).thenReturn(new FileStorage.StoredFile("stored-name", 3))` — decide what the fake answers.
- `verify(repository, never()).save(any())` / `verifyNoInteractions(fileStorage)` — check that a method was (not) called.

|---|---|
| `createSavesAndReturnsTheDto` | create maps, saves and returns the DTO (no file yet) |
| `createWithTakenFileNameFails` | the business rule throws `DuplicateFileNameException` and nothing is saved |
| `updateMayKeepItsOwnFileName` | an attachment can keep its own file name |
| `updateToTheFileNameOfAnotherAttachmentFails` | ... but cannot take another one's |
| `updateOfMissingAttachmentReturnsEmpty` | missing id -> empty `Optional` |
| `deleteRemovesTheAttachment` | delete calls the repository |
| `uploadContentStoresTheFileAndItsDetails` | the file goes to `FileStorage`, the attachment gets type, size and stored name |
| `attachmentWithoutFileHasNoContent` | no file yet -> empty, and the disk is not touched |
| `getAttachmentReturnsTheDto` / `getMissingAttachmentThrowsNotFound` | found -> dto, missing -> `NotFoundException` |
| `getAttachmentsOfOneOwner` | the owner query parameters reach `findByOwner` |
| `createAnswers201WithTheCreatedDto` | status 201 and the body |

## 9. Checklist for a new module

1. Copy the `attachments` package and rename `Attachment` / `attachments` everywhere
   (leave out `storage`, `AttachmentContent` and the two content endpoints unless the module stores files).
2. **Entity**: fields and relations; the table name in `@Table` **and** `@SQLDelete`; enums with `EnumType.STRING`.
3. **Repository**: `entityType()`; custom finders only if needed.
4. **DTOs**: request (validation, no id, ids instead of entities) and dto.
5. **Mapper**: the one-line interface; `@Mapping` lines only for relations.
6. **Exception**: one class per business rule, extending `BusinessException`.
7. **Service**: interface + impl, `@Loggable` on the impl, `@Transactional` on writes, load related entities by id.
8. **REST**: `@Path("/xxx")` without `/api/v1`, `@RequestScoped`, `@NotNull @Valid` on the body,
   `@RolesAllowed` / `@PermitAll` for who may call each endpoint.
9. **Tests**: copy the test classes, add the entity (and the entities it has relations to) to the test `persistence.xml`.
10. Run the tests, deploy, try every endpoint once.

To give your module's entity attachments: add a value to `AttachmentOwnerType` and call
`AttachmentService.findByOwner(...)` where you need them — nothing changes in your entity.

## 10. Common mistakes

| Mistake | What happens | Correct |
|---|---|---|
| `@NotBlank` on `Boolean`, `BigDecimal`, an enum or an entity | every save fails (`UnexpectedTypeException`) | `@NotNull` (or `@Positive`, ...) |
| An enum without `@Enumerated(EnumType.STRING)` | stored as a number; reordering the enum corrupts old rows | `EnumType.STRING` |
| An entity inside a DTO | JSON loops, lazy errors, the client can change anything | the id of the related entity |
| No `@ApplicationScoped` on a repository / service | the injection is `null` or deploy fails | add it |
| No `@RequestScoped` on the API | `@Valid` ignored, `null` injections | add it |
| No `@Transactional` on a write | changes not saved, `LazyInitializationException` | add it |
| A method calls a `@Transactional` method of **its own class** | no transaction is opened (interceptors only see calls from other beans) | put `@Transactional` on the method that is called from outside |
| `@Path("/api/v1/xxx")` | URL becomes `/api/v1/api/v1/xxx` | `@Path("/xxx")` |
| Different table names in `@Table` and `@SQLDelete` | deleting a row soft-deletes a row of **another** table | the same name |
| Redeclaring `id` / `createdAt` in the entity | hides the `BaseEntity` field, audit or `equals` breaks | remove it |
| Returning entities from the service | lazy errors, internal fields leak | return DTOs |
| Injecting `XServiceImpl` | ties the API to one implementation | inject `XService` |
| `@RolesAllowed` on a service | ignored: everyone gets in | on the REST class |
| `@RolesAllowed` on the REST class, no `@PermitAll` on the reads | reading needs a login too | `@PermitAll` on the public methods |
| Two implementations of the same service interface | CDI cannot choose, the whole application does not deploy | one implementation |
| Saving a file under the name the user sent | files overwrite each other; `../` writes outside the folder | a generated name (UUID) |
| Reading a whole file into a `byte[]` | a big file fills the memory | `InputStream` + `Files.copy` |
